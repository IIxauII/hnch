# roadmap.md — hnch v1 implementation plan

This document sketches the path from today's scaffolding to a shippable v1. It is a *map*, not a spec — each phase has a scope and an exit bar, but the class- and file-level shape is determined when the phase is underway, not pre-baked here.

Sibling docs:
- [`project.md`](project.md) — what the product is.
- [`schema.md`](schema.md) — the Yjs doc shape (authoritative).
- [`ux.md`](ux.md) — what the user sees and does (authoritative).
- [`adr/`](adr/README.md) — why each structural choice was made.

Implementation phases are intentionally *vertical slices* — each phase ends at a demonstrable outcome rather than a layer completion. This keeps the project continuously demoable and forces end-to-end thinking early.

## 1. Starting state

What already exists at the moment this roadmap is written:

- `packages/client` — Ionic 8 + Angular 20 + Capacitor 8 scaffold generated by `ionic start`. Nothing hnch-specific yet; `main.ts` still uses the default bootstrap.
- `packages/relay` — a 32-line stub `index.ts` that prints a sanity-check line. No y-websocket server, no handshake, no snapshot store.
- `packages/shared` — two real modules: `room-code.ts` (6-char no-look-alike generator per [ADR-0008](adr/0008-room-code-format.md), covered by `room-code.test.ts`) and `auth.ts` (type skeletons for `JoinCredentials` / `JoinResponse` per [ADR-0009](adr/0009-access-control-relay-tokens.md)). No Yjs doc-shape types yet.
- `mise.toml` pinning pnpm/node/etc. (from scaffolding phase).
- 15 accepted ADRs. [`schema.md`](schema.md) and [`ux.md`](ux.md) current with [ADR-0015](adr/0015-v1-scope-session-level-reveal-and-timer.md).

Concrete implication: Phase 1 starts with real work on three fronts (client bootstrap, shared Yjs types, dev-loop ergonomics) but with all the architecture questions already answered.

## 2. Phases at a glance

| Phase | Name | Exit bar |
|---|---|---|
| 1 | Foundation | Launch app → onboard (first-run only) → land on Home. Routing scaffolded, dark mode respected, Ionic left at its default platform auto-detect. No sync, no real session state yet. |
| 2 | Local session loop | One client plays through a full session locally: Home → Lobby → Estimating → (reveal in Lobby) → re-vote → next round. Manual reveal only, no relay, no timer. |
| 3 | Relay + multi-client sync | Two or more clients create / join / play a session together in real time via a running relay. Manual code-entry join path only. |
| 4 | Timer + host election | Timer-based rounds work reliably. Host drops are handled with a 5-second debounce + lowest-peer-ID election. |
| 5 | Access control + join paths | Password-protected rooms work. Share sheet, QR display, QR scan, and `/join?code=` deep links all resolve to Join. Universal links deferred to Phase 6. |
| 6a | PWA polish | Theme picker, settings screen, reveal animation, haptic wiring, a11y pass. All testable in a browser. |
| 6b | Native iOS build | Capacitor iOS project, universal links, SQLite persistence, on-device smoke test. v1 candidate. |

Each phase assumes the previous one passes its exit bar. Within a phase, ordering is opportunistic — use whatever sequence keeps the dev loop fastest.

## 3. Phase 1 — Foundation

**Scope.** Get the shell working; no session behavior yet.

**Work.**
- Bootstrap: `provideIonicAngular()` in `main.ts` with Ionic's default mode (auto-detected per platform — iOS on iPhone, Material on Android/PWA). See [`ux.md` §2](ux.md#2-app-shell--navigation).
- Angular routing: six routes for the v1 screens — `onboarding`, `home`, `join`, `lobby`, `estimating`, `settings`. Placeholder components, nothing more. Route guard that redirects to `onboarding` on first launch (no stored display name). (Note: a `revealed` route was scaffolded here originally; it was removed when Lobby was updated to show results inline — ADR-0018.)
- `packages/shared`: add `doc.ts` — TypeScript interfaces that mirror [`schema.md`](schema.md) one-to-one: `Meta`, `Settings`, `Participant`, `Round`, `Scale`, awareness payload. These are the types client and relay will share going forward. No Yjs bindings yet (those live in the client — shared is platform-neutral).
- Onboarding screen: name input + Continue button, writes to `@capacitor/preferences`. Handles the pending-join-URL case (if the app launched via deep link before onboarding, stash it and resume to Join after save).
- Home screen: "Create Room" and "Join Room" buttons. Jump-back-in banner can be present as a shell (no wiring yet — that needs Phase 2+).
- Dark mode: respect `prefers-color-scheme`; no explicit theme picker yet (that's Phase 6).
- CI green: existing `room-code.test.ts` and any new shared-package tests pass under `pnpm test`.

**ADRs touched.** None structurally; all referenced: [0002](adr/0002-frontend-framework-angular-ionic-capacitor.md), [0005](adr/0005-device-identity-capacitor-device-plugin.md), [0014](adr/0014-repo-layout-pnpm-workspaces.md).

**Risks.** Low. Most of this is plumbing.

**Exit bar.** `pnpm --filter @hnch/client start` boots, onboarding flow captures a name and persists it, relaunch skips onboarding and lands on Home.

## 4. Phase 2 — Local session loop

**Scope.** Validate the doc shape and UI binding end-to-end, on a *single* client, without a relay.

**Work.**
- Doc service: a client-side service that owns a `Y.Doc`, exposes strongly-typed read/write helpers derived from the Phase-1 shared types, and emits observables for Settings / Participants / current Round. No persistence, no relay — the doc is in-memory.
- Lobby screen: wired to the doc. Shows participants (just you), settings summary, Share / QR placeholders, and "Start Round 1" button.
- Session Settings half-sheet ([`ux.md` §5.8](ux.md#58-overlays)): scale picker, access picker. Access has no runtime effect yet — just writes to `settings`.
- Round-start modal: captures optional descriptor, writes a new Round.
- Estimating screen: 3-column card grid, vote cast + change, avatar row (just you, trivially), host-only Reveal button.
- Lobby post-reveal: results shown inline (grouped by vote value, voter chips, stats). Re-vote (creates Round with `parentRoundId`) and Next Round both work.
- Reveal is **manual only** this phase. Timer UI may render but must not auto-reveal.
- Back-navigation leaves the Lobby, returns to Home. The Jump-back-in banner still isn't wired (it needs persistence / relay state that arrives in Phase 3).

**ADRs touched.** None. Consumers of [0003](adr/0003-state-sync-yjs.md), [0013](adr/0013-round-model-flat-parentroundid.md), [0015](adr/0015-v1-scope-session-level-reveal-and-timer.md). Exercises `schema.md` end-to-end for the first time — flag any field-level ambiguity immediately and fix via schema.md edit + (if shape-level) new ADR.

**Risks.**
- Yjs binding style for Angular. We haven't picked a pattern yet — plain `doc.observe` → `BehaviorSubject`, or a library like `y-angular`/`valtio`-style adapter. Decide in the phase; if the decision is architectural, it gets an ADR.
- `schema.md` is a document — the first concrete use may expose ambiguity (e.g., how Y.Map vs plain object is represented in TS). Treat this as expected and correct the schema as we go.

**Exit bar.** On a single device, you can create a room, configure settings, run Round 1 (vote → reveal), re-vote, run Round 2, and leave back to Home. No network involved.

## 5. Phase 3 — Relay + multi-client sync

**Scope.** Two-or-more clients syncing through a real relay.

**Pre-phase design.** Before writing relay code, decide the connection handshake wire format. [ADR-0009](adr/0009-access-control-relay-tokens.md)'s action items still say "design the invite-flow protocol." This phase cannot ship without a concrete protocol, so either:
- Write a small ADR (**proposed ADR-0016: client ↔ relay connection handshake**) that pins down the wire format for `JoinCredentials` (URL query string? JSON after upgrade? one-shot header? see `auth.ts` comment), or
- Amend [ADR-0009](adr/0009-access-control-relay-tokens.md) via a new superseding ADR if the current one is found to be load-bearing on the undecided parts.

This design work is ~1 hour; resolve it before relay code lands.

**Work.**
- Relay (`packages/relay`):
  - y-websocket server setup with content-blind forwarding ([ADR-0001](adr/0001-networking-crdt-over-relay.md)).
  - Room UUID minting on Create; code ↔ UUID map in memory ([ADR-0008](adr/0008-room-code-format.md)).
  - In-memory snapshot store, 24-hour TTL keyed by room UUID ([ADR-0012](adr/0012-snapshot-policy.md)). No disk.
  - Connection handshake per the pre-phase design decision, but with access control in *permissive* mode (every join accepted). Real access control is Phase 5; here we just validate the *handshake shape*.
  - Health endpoint (`GET /health`) for local dev and future deploys.
- Client:
  - y-websocket provider wired to the relay URL (env-driven).
  - Join Room screen: manual code entry path only. No QR, no URL deep link yet.
  - Awareness: publish `participantId` on connect; derive "online" set on every screen that shows participants.
  - Jump-back-in banner on Home: local store of `{ roomCode, roomUuid, lastScreen, lastSeenAt }`, cleared when relay reports unknown-room.
  - Back-button behavior: disconnect on leave, keep local banner for rejoin.
- Dev loop: root script or mise task that runs client and relay together (e.g., `pnpm -r dev` with concurrent watchers).

**ADRs touched.** Likely one new ADR (connection handshake) before coding. No supersedes — [ADR-0009](adr/0009-access-control-relay-tokens.md) stays and gets cross-referenced.

**Risks.**
- Reconnection semantics after network blips: we want the peer to rejoin automatically without the user tapping Jump-back-in, if the blip is short. Decide what "short" means.
- Awareness vs participants map divergence: every screen that shows presence needs a clear rule for which source is authoritative for what (see schema.md's derived-state section).

**Exit bar.** Two browsers (or browser + simulator) on different machines / ports can create/join a room via manual code entry, both see each other in the participants list, and either can observe the other's Round / vote state updating in real time. Manual reveal works across clients.

## 6. Phase 4 — Timer + host election

**Scope.** Robustness — the two coordination-flavored features that make the product feel reliable.

> **Note:** The countdown-timer portion of this phase was later superseded by [ADR-0018](adr/0018-remove-timer-add-unanimous-reveal.md), which removed `revealMode` / `timerDurationMs` and replaced countdown-triggered reveal with unanimous auto-reveal. `timerStartedAt` is retained as a stopwatch origin. The host-election work below shipped unchanged.

**Work.**
- Timer — originally a per-session countdown ([ADR-0011](adr/0011-timer-authority.md), [ADR-0015](adr/0015-v1-scope-session-level-reveal-and-timer.md)), then replaced by elapsed-time stopwatch + unanimous auto-reveal ([ADR-0018](adr/0018-remove-timer-add-unanimous-reveal.md)):
  - `round.timerStartedAt` written at round creation; all clients display elapsed time counting up.
  - When all online voters have cast votes, any client writes `round.revealedAt` (unanimous auto-reveal). Host can also reveal manually at any time.
- Host election ([ADR-0010](adr/0010-host-election.md)):
  - `settings.hostParticipantId` read and observed.
  - Client-side liveness check: awareness has an entry for the current host? If not, start the 5-second debounce; if absence persists, the client with lowest peer ID writes itself into `hostParticipantId`.
  - "Alice is now hosting" toast on change.
  - "No reclaim": prior host reconnecting after the handoff does not reclaim automatically.
- Tests:
  - Unit: election-lowest-peer-ID logic.
  - Integration: a "simulated disconnect" test that runs two Yjs peers and verifies host handoff.

**ADRs touched.** [ADR-0018](adr/0018-remove-timer-add-unanimous-reveal.md) (supersedes 0011 and 0015); [ADR-0010](adr/0010-host-election.md) unchanged.

**Exit bar.** Kill the host client mid-round; within ~5 seconds, one of the other clients becomes host and the round continues.

## 7. Phase 5 — Access control + invite paths

**Scope.** Private rooms, join paths (share, QR, deep link), and expired-room handling. Invite-only was dropped from v1 per [ADR-0017](adr/0017-password-hashing-drop-invite-only.md); universal links deferred to Phase 6 (requires native iOS build + deployed domain).

**Pre-phase design.** [ADR-0017](adr/0017-password-hashing-drop-invite-only.md) resolved the outstanding ADR-0009 action items: PBKDF2-SHA-256 via Web Crypto for password hashing, invite-only dropped, `PATCH /rooms/:uuid/access` for mid-session access changes. Invite URL format decided as `https://hnch.app/join?code=XXXXXX` (query param, configurable via `environment.appBaseUrl`).

**Work.**
- Relay:
  - `POST /rooms` accepts optional `passwordHash`; `PATCH /rooms/:uuid/access` for mid-session access changes.
  - Password enforcement on WS upgrade with `timingSafeEqual`.
- Client:
  - Access picker on Session Settings writes the chosen mode; host's create-room / update-settings flow registers the credential with the relay via `PATCH`.
  - Join Room screen: renders the password field inline when the entered code resolves to a password-protected room; surfaces error toasts for the rejection reasons.
  - Share sheet (`@capacitor/share`) from the Lobby Share button with clipboard fallback on web; content per `ux.md` §6.
  - Deep-link join via `/join?code=` query param with onboarding resume support.
  - QR display modal on Lobby: full-screen `ion-modal` with invite URL encoded as a large QR via `qrcode` library.
  - QR scanning on Join Room via `@capacitor-mlkit/barcode-scanning`; auto-submits on valid scan, shows password field if room is password-protected.
- Expired-room handling: when relay returns `unknown-room`, show the toast + return to Home (per `ux.md` §4.6).

**ADRs touched.** [ADR-0017](adr/0017-password-hashing-drop-invite-only.md) — password hashing scheme and invite-only removal.

**Risks.**
- QR scanning on web relies on the browser's `BarcodeDetector` API or ZXing fallback — quality varies by device. Native ML Kit scanning (Phase 6) will be more reliable.
- `PATCH /rooms/:uuid/access` has no host authentication in v1 — mitigated by UUID unguessability, flagged for future hardening.

**Exit bar.** A user can create a password-protected room, share the invite URL, and have another user join via (a) QR scan, (b) manual code entry with the password, or (c) `/join?code=` deep link. Invalid / expired cases produce the expected error states. Universal link interception (native OS opening the app directly from a tapped URL) lands in Phase 6 alongside the iOS build.

## 8. Phase 6a — PWA polish

**Scope.** UI polish, theming, accessibility, and animations — everything testable in a browser without a native iOS build.

**Work.**
- Theme: Settings screen with display-name editor and theme picker (System / Light / Dark). Persist via Preferences; apply pre-first-paint.
- Settings screen's remaining content: version, open-source licenses, privacy.
- Reveal animation (staggered 80 ms fade-in-up) — easy to add late, intentionally deferred to polish.
- Haptics (`@capacitor/haptics`): wire the full haptic map from `ux.md` §6. The plugin is a no-op on web, but the wiring can be written and structurally verified now; actual feedback fires once the native build lands.
- Accessibility sweep:
  - VoiceOver labels on non-text interactive elements (estimate cards, QR buttons, avatar rows).
  - Verify touch targets on the smallest supported iPhone (Safari responsive mode).
  - `prefers-reduced-motion` → instant transitions for reveal and card-press animations.
- Apple HIG review checkpoint (visual): verify look and feel in Safari iOS simulator / responsive mode. Fix regressions before moving to native.

**ADRs touched.** None expected.

**Risks.** Low. All work is verifiable in a browser.

**Exit bar.** PWA in mobile Safari looks polished: theme picker works, reveal animates, a11y labels present, reduced-motion respected. Settings screen is complete. Ready for native build.

## 9. Phase 6b — Native iOS build

**Scope.** Capacitor iOS project setup, native-only features, and on-device validation.

**Requires:** Apple Developer account, Xcode, physical iPhone for testing.

**Work.**
- Native iOS build via Capacitor: `npx cap add ios`, ensure all Capacitor plugins (Preferences, Haptics, Share, Device, MLKit BarcodeScanning) resolve correctly on native.
- `NSCameraUsageDescription` in Info.plist for the QR scanner.
- Universal links: Apple App Site Association (AASA) file on `hnch.app/.well-known/`, Associated Domains entitlement in Xcode, `App.addListener('appUrlOpen')` handler to parse incoming URLs and navigate to `/join?code=`. The client-side `/join?code=` handling already works from Phase 5; this step wires the native OS interception so tapped links open the app directly instead of Safari.
- Capawesome SQLite persistence ([ADR-0004](adr/0004-local-persistence-sqlite-indexeddb.md)) on native: Yjs provider's IndexedDB path swapped for SQLite on native. PWA keeps IndexedDB.
- Verify haptics actually fire on device (wiring landed in Phase 6a).
- Dev-device smoke test on a real iPhone: install, onboard, create a room, have a second device join, play a full round.
- Apple HIG review checkpoint (on-device): final pass on a real device for layout, safe area, keyboard behavior, and haptic feel.

**ADRs touched.** None expected; any implementation surprise surfaces as a new ADR.

**Risks.**
- iOS Capacitor native quirks we don't yet know about (Keyboard, SafeArea, deep links). Time-box troubleshooting and, if blocked, pull the offending item from v1.

**Exit bar.** A fresh install on a physical iPhone runs through the happy path (create / invite / join / vote / reveal / re-vote / next round / leave / jump-back-in) with no crashes and no visible layout regressions. v1 candidate.

## 10. Cross-cutting concerns

These apply across phases; flagging them once here saves repeating per phase.

**CLI parity.** The `@hnch/cli` package (`packages/cli`) is a terminal client that ships alongside the mobile/PWA client. It uses the same relay protocol and `@hnch/shared` doc schema. Any session-behavior change (rounds, reveal, host election, access control, scales) must be reflected in both clients. See [`cli.md`](cli.md) for commands and conventions.

**Tests.** We are not writing a separate test-strategy document for v1. Rule of thumb:
- Pure shared utilities get unit tests (as `room-code.ts` already does).
- Yjs-coordination edge cases (timer fallback, host election) get simulation tests where feasible — two or more in-process peers against a mock transport.
- UI screens are exercised by manual smoke tests; no Karma/Cypress investment in v1.

**Error handling.** Network errors bubble to toasts, not console. Relay rejections map to the `JoinRejectionReason` enum and produce user-facing copy from one source.

**Logging.** Client: `console.debug` gated behind a boot-time flag. Relay: plain `console.log` with a small structured prefix; no log framework in v1.

**Deploy.** Relay deployment is covered by [ADR-0029](adr/0029-relay-deployment.md): bare-metal VPS, Caddy reverse proxy, systemd, auto-TLS, single-origin `hnch.dev`. Bootstrap script, Caddyfile, and systemd unit live in `infra/`. Client distribution (TestFlight for iOS, static hosting for PWA) is post-v1.

**ADR hygiene.** Any phase that discovers the architecture is under-specified writes a new ADR *before* the code that depends on it. The current roadmap flags two likely candidates: the ADR-0009 connection handshake (Phase 3) and the access-control wire details (Phase 5).

## 11. Explicit non-goals for v1

These are *not* in this roadmap and will be called out if they drift in:

- iPad-specific or landscape-first layouts.
- Android-native or desktop-native flavors (PWA is the non-iOS v1 path).
- Session history / reporting / analytics surfaces beyond the single Jump-back-in banner.
- Team UI (the [ADR-0007](adr/0007-teams-local-only.md) concept stays in architecture, no UI in v1).
- Integrations with trackers (Jira, Linear, etc.).
- Account sign-in or cross-device identity.
- Export formats beyond a future clipboard markdown dump ([ADR-0013](adr/0013-round-model-flat-parentroundid.md) action item, not v1).
- Consensus indicator in Lobby results ([`ux.md` §8](ux.md#8-open-ux-questions)).
- Liquid Glass / iOS 26 theme ([`ux.md` §7](ux.md#7-theming)).
